# The MPFree USB creator: a boot stick with no terminal

**Status:** built, 2026-11-15 ([as built](#as-built-2026-11-15)); made sticks on Linux for creator rounds 1 to 3 and the final device round on the reference MPC (15 and 16 Nov). Added on 2026-11-16: the [release workflow](#releases), the setup script switching [developer mode off](#developer-mode-afterwards) (not yet run on the MPC), and fixes to the Windows and macOS writers (not yet tried on a stick); the [creator round](../hardware/usb-creator-round.md) is the runbook that tries them on the reference MPC. The plan was a proposal the owner approved the same day ([decisions](#the-owners-decisions-2026-11-15)). It is a desktop app for Linux, macOS and Windows that turns a musician's own copy of Akai's 3.10.1 update into an MPFree boot stick, and a one-time, terminal-free way to set up the MPC for it. The boot itself is the merged soft-reboot route in [How MPFree boots from the stick](../hardware/soft-reboot-boot.md); the only change to it is an MPC One board check in the hook ([below](#safety-work-before-anyone-else-runs-it)). The musician's steps are in the user manual: [Installing MPFree](../../user/src/getting-started/installing.md).

## The goal

An average musician who wants to try MPFree should get from "my MPC runs 3.10.1 and I have Akai's update file" to "MPFree starts when the stick is in" without a terminal, SSH, keys, scripts or a network cable. The project never hosts or bundles any Akai file.

Out of scope: updating the MPC to 3.10.1. The musician does that first with Akai's own instructions and keeps the update file Akai gave them. The creator starts from there.

## Installing the hook without a terminal

**Yes, it can be done with no terminal: by the stick itself, through Akai's own script runner.** On 3.10.1, with developer mode on, Akai's app offers to run `autorun.sh` from a USB drive and runs it as root after one tap. This was tested on the reference MPC on 2026-11-15 ([record](../hardware/stick-autoboot.md#what-the-script-runner-test-showed-2026-11-15)): the prompt came once Akai's app was up, and the script ran as root through `systemd-run` (a transient `autorun-sh.service`), from a FAT32 stick mounted `noexec` (a shell script is read by `sh`, so `noexec` doesn't stop it). It was rejected as the *boot* trigger because it needs a tap on every boot after Akai's app has drawn. For a **one-time setup** that tap is exactly what we want.

### The setup script

The creator adds a small FAT32 partition, partition 5 (`mpfree-setup`, volume label `MPFREE`), between partitions 3 and 4 on the disk (partition 1 must stay `mpfree-test-root`, as the hook requires). It holds:

- `autorun.sh`: a thin wrapper that runs the steps below with `sh` and writes everything it prints to `MPFREE-SETUP/setup-log.txt`;
- `hook-install.sh`, byte for byte as on main, so the files it writes and its undo stay exactly the ones already tested;
- `mode.txt`: `install` or `remove`, set by the app (so the same stick can uninstall; see below), and `removed` once the script has removed the hook.

The wrapper runs, in this order, and stops at the first failure, writing why:

1. **Checks** (read-only): the board is an MPC One (`compatible` names `inmusic,acva`), the kernel release equals the one the stick was made for, MPFree's stick is in, no firmware updater is running, and nothing is at `/run/nextroot` (where a plain restart would turn into a soft-reboot).
2. **The hook install**: `hook-install.sh` writes its three files on `/data` and runs the hook's own read-only check of the stick, ending in a `RESULT:` line. This is the only change to the MPC's own files.
3. **Developer mode off, and the restart**: Akai's own off script, `/usr/lib/az0x/user-access/disable.sh`, which deletes `/data/root` and `/data/ssh` (developer mode's root login, its SSH settings and any keys added there) and restarts ([below](#developer-mode-afterwards)); then `systemctl reboot`, which is only reached if Akai's script returns without restarting. A stick with developer tools (`mpfree-dev/` on partition 5) or a file named `keep-developer-mode` there keeps developer mode on and restarts plainly, as does an MPC without that script. With the stick in, MPFree starts, and its setup wizard takes over.

The whole script takes seconds, so nothing depends on how Akai's app treats a long script.

The script never writes the root filesystem, the boot partitions or the U-Boot environment. Apart from the hook's three files, the one change is Akai's own: developer mode off, which the musician undoes in Akai's menu.

**Showing the result.** The MPC restarting into MPFree is the sign the hook went in. If the script stops early, the MPC doesn't restart and stays in Akai's app; `setup-log.txt` says why, and the app shows it when the stick is next plugged into the computer.

**Uninstall.** Taking the stick out is always enough to get Akai's MPC back. To remove the hook's files too, the app's **Take MPFree off my MPC** tab walks through three numbered steps; its **Make it a removal stick** button (`mpfree-stick setup-mode --device DISK remove`) sets `mode.txt` to `remove` and renames partition 1 to `mpfree-test-root-off` in the partition table. The hook looks only for a partition named `mpfree-test-root`, so with the hook still on the MPC, the musician can switch on with the stick in and Akai's system starts; no change to the hook. The next run of the setup script (developer mode on, tap Yes) runs `hook-remove.sh`, which deletes only files carrying the hook's marker line, writes `removed` in `mode.txt`, and restarts, switching developer mode off again as the install does. If Akai's app offers the script again after the restart, tapping Yes says there is nothing to do and doesn't restart, so there is no loop. **Make it an MPFree stick again**, in the same tab's "Changed your mind?" panel (`setup-mode ... install`), names partition 1 `mpfree-test-root` again and writes `install`: the partition table returns byte for byte to what it was.

### The first-start wizard: backup, kits and samples

On its first start, MPFree runs a setup wizard before the pad player, with a progress bar. Each step done is recorded in the store (`settings/setup.conf`, owner `setup`: `done=backup,kits,kit folders,kit files`, the backup's folder, how many kits and samples; a step this version no longer has, such as round 4's `samples`, is dropped) as it ends, and the try's number before anything runs, so each step runs once even if a later one is cut off; a failed start is tried again at the next, at most three times, and the pad player plays meanwhile. The store opens before the wizard, so a new partition 4 is marked as MPFree's (`FORMAT`) before the backup or the library is written there ([storage spec](storage-spec.md#layout-of-the-partition)); the third creator stick wrote them first, its store refused the folder, and so nothing was saved and BROWSE had no library. When the store names no backup, the newest finished one on partition 4 is used (a folder the service has named, with its `SHA256SUMS` and `MANIFEST.txt`; a half copy keeps `.part`), so a start whose record was lost doesn't back the MPC up again. Without a store that saves, the wizard doesn't run, since nothing it did would be kept. A rewritten stick keeps partition 4, so nothing runs again: that is the creator's **Update MPFree on this stick** ([below](#updating-a-stick)). A step added in a later version (the MPC's keygroup instruments, after #382) runs alone on a stick set up before, from the backup it already has. It runs only on sticks that have the backup service (the creator's).

**1. "Backing up your MPC": a read-only eMMC window.** Every start of MPFree switches the eMMC and SD card off before udev or any mount ([the switch-off](../hardware/soft-reboot-boot.md#switching-off-the-internal-storage)); that stays exactly as it is. The wizard then asks a small root service, `mpfree-setup-backup.service`, to open a short window. The pad player never does it itself: with `--app-user` it isn't root, and anything that needs root goes in its own unit ([safety rules](../../agents/README.md)). The service:

1. checks that no `mmcblk*` device exists, that every Akai unit that can touch a disk is still masked, and that partition 4 has room, after removing any half copy (`backup/mpc-one-emmc-<UTC>.part/`, never a link) that an earlier try left when the power went;
2. binds **only the eMMC controller** (`ff0f0000`) again; the SD card stays off. The stick's udev rule for `mmcblk*` devices already sets `SYSTEMD_READY=0` and `UDISKS_IGNORE=1`. A second rule, in `/run` for the window only, writes `1` to each eMMC disk's `force_ro` file as it appears (the user area, `boot0` and `boot1`), and the script writes it again itself: the MMC driver then marks the whole disk read-only, every partition with it. Akai's system has no `blockdev` (BusyBox without that applet), so the window uses the kernel's own switch; the first creator stick stopped here on 2026-11-15;
3. checks that the whole disk and every partition read as read-only (`ro` 1), and every disk's `force_ro` is 1, or switches it off and stops;
4. reads every write and discard counter of the disk and its partitions;
5. copies the user area (7.28 GiB), `boot0` and `boot1` (4 MiB each) with MPFree's own `mpfree copy-image` ([`imagecopy.rs`](../../../rust/mpfree-app/src/imagecopy.rs): the disk opened read-only, 1 MiB blocks straight to a file made new, and every MiB of zeros left as a hole) to `backup/mpc-one-emmc-<UTC>.part/` on partition 4, while `sha256sum` hashes the same disk from the eMMC beside it, after checking the disk layout and eMMC model as `host_emmc_backup.py` does (renamed to `backup/mpc-one-emmc-<UTC>/` when verified; root's, readable by the pad player's group). The eMMC reads at about 40 MB/s, faster than the stick writes, so the hash costs no time. While it copies, `vm.dirty_bytes` is 32 MiB (RAM only, put back afterwards, also on failure): the copy runs at most that far ahead of the stick, so the file's size, which the progress shows, is what the stick holds, and there is no long flush at the end. Every 30 s the kernel log gets the pace: MiB copied, KB/s, what the block layer has read from the eMMC and written to partition 4 and to the whole stick, how busy the stick was, and what waits in memory, so a slow side shows which it is. Before the copy it logs the stick's USB speed and largest transfer, and after each disk how much the copy wrote and how much it left as holes;
6. reads the counters again: **no write or discard on any partition**, p7 and p8 included. This is stricter than today's backup, where Akai's system has p7 and p8 mounted read-write; here nothing has them mounted, so the backup is a clean, quiet copy;
7. unbinds the controller, checks that no `mmcblk*` device is left and removes stale links. If the controller can't be switched off again, the MPC powers off, as the startup switch-off does;
8. drops the page cache, reads the backup back from the stick, hashes each image again and compares it with the eMMC's hash (no `sha256sum -c`: one option fewer to need of Akai's BusyBox). Its progress is the stick's block layer read counter, against what the copy wrote (a hole reads as zeros without reading the stick). Then it writes `MANIFEST.txt`, whose `MPC:` line tells this MPC's backups from another's: the first 16 hex digits of the SHA-256 of `mpfree-mpc:` and the device tree's `serial-number` (U-Boot's; NUL bytes left out), or `unknown` without one. The number itself is never written.

A stop from systemd (its own timeout, two hours, or a shutdown) mid-copy is caught: the copy and the hash are stopped, `vm.dirty_bytes` put back, the window closed and the half copy deleted.

The eMMC is reachable only during step 5's copy, which is limited by the stick's write speed on the MPC One's USB 2.0 port (about 7.5 MB/s measured on the reference MPC): roughly 10 to 20 minutes, plus a few to read it back. Any failure leaves the eMMC switched off; the wizard says what happened, and the pad player still works.

**Why no `tee`.** The second creator stick (2026-11-16) copied at about 80 KB/s: "0.1 of 7.8 GB" after 20 minutes. Its copy ran `dd | tee FILE | sha256sum`, and Akai's BusyBox `tee` is built without block I/O: it moves the stream with `getchar` and `putc` on unbuffered streams, one `write` per byte for each output. The same pattern measured 260 times slower than block I/O on a workstation; on the MPC's RT kernel that lands at the rate seen. The eMMC itself had come up at its normal 50 MHz DDR, and read at 40.5 MB/s in the earlier SSH backup.

**Why holes.** The third creator stick (2026-11-16) still took 30 to 40 minutes to copy: `dd` wrote all 7.8 GB to a stick that writes about 7.5 MB/s on the MPC, and Akai's `dd` has no `conv=sparse`. About half of the MPC One's eMMC is unused (the root filesystem 382 of 500 MiB, the content partition 3.0 of 3.9 GiB, the data partition 201 MiB of 2.7 GiB). `mpfree copy-image` checks each MiB and, when it is all zeros, only grows the file's size instead of writing it. The file reads back exactly as the disk, so its SHA-256 is the disk's, and the computer's copy and the kits import read it as before (`mpfree-diskimage` reads holes as zeros). How much it saves depends on how much of the unused space reads as zeros: space that never held a file does; a deleted file's blocks may not. The log says what each copy wrote. The program is MPFree's own, on the stick (`/etc/mpfree-test/mpfree`), so it is not in `NEEDS`; the service stops first if it is missing. It runs before anything else in `main`, opens the source with `File::open` only, and creates the file with `create_new`, so it never overwrites a file or follows a link.

**Other writes on the same stick during the copy.** Two other writers shared the stick with the third stick's copy, and both are cut down: the log service rewrote its copies of the logs every 10 s on a log partition mounted with `sync`, so each of about a hundred small writes waited for the stick (now mounted without it; the `sync` at the end of each round writes them at once); and the kernel zeroes partition 4's inode tables in the background after its first mount (ext4lazyinit), about 0.95 GB on a 64 GB stick at mke2fs's default of one inode per 16 KiB, now about 120 MB at one per 128 KiB (`-i 131072`: still over 100,000 files on a 16 GB stick). The pace lines show both: partition 4's writes beyond the copy's are the inode tables, and the whole stick's beyond partition 4's are the logs.

**2. "Extracting Akai drum kits and samples".** From the backup on the stick when there is one: the wizard reads the content partition (p7) inside `mmcblk0.img` read-only. With the backup left out, it reads p7 itself through the read-only window ([below](#leaving-the-backup-or-akais-kits-out)); either way it
- makes drum kits from the factory drum programs, as `offline-factory-kit.py` does today (`.xpm` files of type Drum, their samples converted to the pad player's kit format), saved on partition 4;
- puts Akai's factory samples into an "Akai factory" folder in MPFree's library on partition 4, sorted into folders so they show up in BROWSE ready to use (`setup::akai_layout`):
  - each drum program (a kit) gets a folder of its own right inside Akai factory, named as the program, with every sound its pads play (all instruments, every active layer);
  - each keygroup (or other) program gets `Instruments/<name>`;
  - the sounds in no program go to `Other sounds/<Akai's folder>`, with a demo project's `_[ProjectData]` dropped from the name;
  - MPC Documents (the musician's own projects on the MPC) and macOS's `._` files are left out. A program with the same name and sounds as one before it (a kit in two demo projects) is left out; other names that are taken get " 2", compared without case so the layout also fits a FAT card. The same backup always gives the same layout, so the next step finds each pad's file there.
  - **Kit files** (step `kit files`): each drum kit's folder gets its `kit.txt` ([browser](browser.md#kit-files)), so BROWSE shows it as a kit and loads it whole (`setup::kit_text`). It is the sampler's part for one kit (`mpfree-sampler 1`, `kits = 1`): pads 1-16 each play their sound from the folder, read from the program as the kits file reads it (`ProgramFiles::pads`, by pad number or by note, whichever finds more), with every other setting as a new pad has it. Only the text is written: the sounds are the folder's own. The files are written without a sync each and synced once. A `kit.txt` already there stays, unless it is a cut-off copy of this one (a power cut before the sync: empty, part of it, or zeros), which goes to the Trash and is written again. A stick set up before runs this step alone at its next start.

  A sound in two kits is in both folders as one file: the second is a hard link (`Library::link_file_unsynced`; a copy where the file system has no links). There are thousands of files (about 3 GB), so each is written without its own sync and the whole lot is synced once at the end (`Library::write_new_unsynced`, `new_folder_unsynced`, then `sync`): a sync per file costs two flushes of the stick, and the third creator stick copied at about 1 MB/s that way. A file kept from a try that was cut off counts only if its size is right; a short one goes to the Trash and is copied again. After 20 samples in a row that can't be put in place, the step stops and says why, instead of trying thousands more on a stick that has stopped taking writes.

  **Sticks set up before (round 4).** Up to round 4 the step was called `samples` and copied Akai's tree as it is: Akai factory held "Expansions" and "MPC Documents", and "Expansions/MPC One" held about 4,000 sounds in one folder, which took minutes to list. The step is now `kit folders`, so a stick that has `samples` done runs it at its next start, from the backup it has. A sound that is already in Akai's own folders is moved into its kit folder (`Library::move_file_unsynced`, a rename: no copy), and what is left of the old folders (MPC Documents with them) goes to the Trash, where Put back undoes it. The log says how many sounds were already there, moved, shared with a kit and copied.

This is `mpfree-factory`'s import (`Content::from_disk`), a Rust port of `offline-factory-kit.py`. The Python tool stays the reference: the same backup must give the same kits. The kits are saved as `library/Kits/Akai factory kits.mpfkits` and loaded at every start before MPFree's own (16 in all); the samples go to `library/Samples/Akai factory/`, sorted as above, all through `mpfree-library`.

**Akai's programs only.** The stick's scripts run on Akai's system, whose BusyBox lacks some applets (`blockdev`) and options (`od -t`, `dd conv=`, and `tee`'s block I/O). Each script names every program it runs in a `NEEDS='...'` line and stops, touching nothing, if one is missing; the creator reads those lines and makes no stick from an update whose system lacks one (`stick::apply`). The tests run each script with only those programs on `PATH`, with an `od` that refuses `-A` and `-t` and a `dd` that refuses `conv=`, `iflag=`, `oflag=`, `ibs=`, `obs=` and `status=`, as the MPC's do. The format step clears its mark through the shell's read-write redirection (`1<>`), which never truncates, since there is no `conv=notrunc`; the second creator stick stopped there.

### Progress the musician sees

The musician waits twice before playing, and each wait says what it is and how far it is:

- **Preparing the stick (seconds).** `setup-format.sh` makes partition 4's filesystem before the pad player can start, with a 64 MiB journal (`-J size=64`: mke2fs zeroes the journal, and its default for a 64 GB stick, 256 MiB, took 37 s of the second stick's first start) and one inode per 128 KiB (`-i 131072`, [above](#the-first-start-wizard-backup-kits-and-samples)). It reports in `/run/mpfree-setup/format-status`: `state` (`checking`, `running`, `done`, `none`, `failed`), `done` (bytes the block layer has written to the partition since mke2fs started) and `total` (64 MiB plus 1/8192 of the partition; mke2fs writes the journal and about 5 MiB of metadata for 61 GB). The creator adds a drop-in to the splash unit (`mpfree-test-splash.service.d/mpfree-setup.conf`, `MPFREE_SETUP_STATUS`), so `mpfree-startup` stays after its scene and draws the pad player's loading card over the last frame, "Preparing the stick for its first start", with MB written and time left, until the state is final (`mpfree_startup::setup`). On a later start the state is `none` within a few seconds, before the pad player could start anyway, so the startup screen ends as before.
- **The wizard (20 to 30 minutes).** One bar for the whole setup (`setup::Estimate`): each stage's share is its expected time, from the bytes it moves (the copy, the read-back, the samples) or the kits it makes, at the rate measured after 10 s, or a first guess before that (12 MB/s copying, holes included; 35 MB/s reading back; 2 kits a second; 3 GB of samples at 5 MB/s). The bar moves with the bytes, never backwards, and the card says the time left for the whole setup once a rate is measured.

The pad player asks for the backup by creating `/run/mpfree-app/setup-backup.request`; `mpfree-setup-backup.path` starts the root service, which removes the request and reports in `/run/mpfree-setup/status` (`key=value` lines) for the progress bar.

**3. Done.** The pad player opens with the MPC's own kits and samples, plus MPFree's own kits. The last page reminds the musician to switch developer mode off.

**The backup belongs on the computer**, not only on the stick. The app's **Copy my MPC's backup** copies the newest `backup/mpc-one-emmc-<UTC>/` off partition 4 (it reads ext4 itself) to a folder the musician can see (MPFree backups in their home folder), into a `.part` folder first, checks every hash, and only then gives it its name. Files are streamed a window of 65,536 blocks at a time (`Ext4::copy_file`), so the 7.3 GiB image copies like any other file; round 4's copy stopped at "files over 4 GiB" because the block map was built whole, and capped there. The limit is now 1 TiB. It doesn't free the space on the stick: that would mean writing ext4 from the computer. A musician who never returns to the computer still has it on the stick.

What the backup is for, said plainly in the app: a full copy of the MPC as it was, including the musician's own projects and settings on p8. It is the starting point for any future recovery, but restoring the boot parts of the eMMC is not possible yet: MaskROM recovery is unproven ([recovery tiers](../research/recovery-and-os-strategy.md)). It holds the musician's data and the unit's identifiers, so it stays on their own stick and computer and is never uploaded. The same goes for the kits and samples.

**Why this order.** It was the owner's call (2026-11-15). Akai's app runs only a seconds-long script, so it doesn't matter whether it would put up with a long one or time it out. MPFree shows real progress on its own screen. And the backup is cleaner, because Akai's system isn't running. The price is the read window: the first moment the eMMC is reachable while MPFree runs. It is read-only and checked by the counters, but it is a change to the boot's safety design. The owner approved it on 2026-11-15, on condition that it is tested on the reference MPC first ([below](#safety-work-before-anyone-else-runs-it)).

### Leaving the backup or Akai's kits out

The owner's [decision 11](#the-owners-decisions-2026-11-15) (17 Nov). Each of the two long steps can be left out of the first start, and asked for at a later start.

- **The creator.** Step 3 of a new stick (and **Erase everything and start over**) has two ticked boxes under "On the first start": **Back up my MPC** and **Bring in Akai's drum kits and samples**, each with a line on what it is and that Prefs can do it later. An unticked box passes `--no-backup` or `--no-akai-kits` to `write`, which puts the words (`backup`, `akai-kits`) in `/etc/mpfree-test/leave-out` on partition 1 (`stick::LEAVE_OUT_FILE`) and a line in `made-by.txt`. The done page says what the first start will do and how long it takes (`first_start_text`). Under **Keep my backup, settings and files**, **Bring in Akai's drum kits and samples too** passes `--akai-kits`: a token in `/etc/mpfree-test/akai-kits` (`stick::AKAI_KITS_FILE`), honoured once, as **Back up my MPC again too** is. `write` refuses `--no-backup` with `--new-backup`, and `--no-akai-kits` with `--akai-kits`.
- **The wizard.** It reads the stick's words once, while the store has no `leave-out` record, and saves them (`leave-out=none` or `backup,akai-kits`), so a later update can't change what the musician chose; from then on only Prefs changes it. The steps it runs are the ones not left out (`setup::steps_wanted`); with both left out it doesn't run. A left-out backup isn't made, but one already on the stick still serves for the kits.
- **Akai's kits without a backup: the content window.** The pad player creates `/run/mpfree-app/setup-content.request` instead of `setup-backup.request`; the same path unit starts the same root service (`setup-backup.sh`), which runs steps 1 and 2 of the backup unchanged (the checks, the read-only window, the layout, the counters) and then, instead of the copy, gives the pad player's group read access to **the content partition's device alone** (`/dev/mmcblk0p7`, owner root, group 960, mode 0440; `/dev` is RAM) on a disk the kernel already holds read-only. It says `state=open`, `step=reading`; the pad player opens the device read-only and reads Akai's kits and samples from it with the same read-only ext4 reader it uses on a backup's image (`Content::from_partition`), writing a counter to `setup-content.alive` every few seconds from a thread of its own (`setup::ContentWindow`), and creates `setup-content.done` when it is finished, or when it stops for any reason (the window's `Drop`). The service closes the window on `done`, or when the counter stands still for 120 s (the pad player stopped), or after an hour at most; it then checks that **no write or discard counter moved** and every disk is still read-only, closes the window as in step 7, and says `state=done`. A counter that moved fails the setup, and the kits made are not counted done. The pad player never deletes the request, counter or done file: the service does. Partition 4 needs 4.2 GB free for the kits and samples (the backup's 7.9 GB check is not made).
- **Prefs.** MPFree's Prefs has **Backup and Akai kits** just before Touch screen ([layout spec section 5](layout-spec.md#5-prefs-shift--menu)), whose two rows show each step's state (made on which day, left out, in BROWSE, at the next start) and ask for it at the next start, or take the ask back. The asks are store records (`fresh-backup=prefs`, `akai-kits-next`), honoured at the next start like the creator's tokens: tries start again at 1, and the backup is not left out any more once made. Nothing runs while MPFree plays; the row's line says the power button's Restart starts it now. On a stick without the setup service the rows say "Not on this stick".

The direct read is a new use of the read-only window: before it reaches anyone it is tested on the reference MPC in the [creator round](../hardware/usb-creator-round.md)'s block C11, with the kits compared to those a backup gives.

### Options considered for the hook install

| Option | Verdict | Why |
|---|---|---|
| **A. Setup script on the stick, run once by Akai's script runner** | **Recommended** | No terminal, no network, no keys. One tap. Uses Akai's documented developer mode. Reuses `hook-install.sh` unchanged |
| B. The app connects to the MPC over the network (developer-mode SSH) | Developer path only | Needs a cable or Wi-Fi, finding the MPC's address, firewall prompts, and Akai's SSH, which takes root with no password until locked. Today's tools already do this for developers |
| C. The developer panel's on-screen terminal, typing one command | Rejected | Still a terminal |
| D. No hook: the script runner starts MPFree on every boot | Rejected by the owner | A tap on every boot, after Akai's app is up |
| E. A unit in Akai's root filesystem, or U-Boot booting USB | Forbidden | Root filesystem and U-Boot writes ([safety rules](../../agents/README.md)) |

### Developer mode afterwards

While developer mode is on, the MPC runs root SSH with no password on any network it is connected to ([compatibility page](../hardware/firmware-3.10.1-compatibility.md)). So it should be off once the setup is done, and a musician can't be relied on to come back for it.

**As built (2026-11-16, the owner's choice):** the setup script ends with Akai's own off script, `/usr/lib/az0x/user-access/disable.sh`, instead of a plain `systemctl reboot`. The offline survey of 3.10.1 read it as `rm -rf /data/root /data/ssh` followed by a restart ([stick test, phase 1](../hardware/firmware-3.10.1-stick-test.md#phase-1-results-2026-11-13)): it is what the menu's off switch is understood to do. The hook's files live in `/data/system/etc/overlay` and `/data/mpfree-hook`, which it doesn't touch. If the script is missing, or returns without restarting, `autorun.sh` restarts plainly after 20 s. It is skipped, and developer mode stays on, for a developer's stick: one with developer tools on partition 5 (`mpfree-dev/`, which need developer mode's SSH) or a file named `keep-developer-mode` next to `autorun.sh`, which anyone can put on the `MPFREE` drive from a computer. Undo: switch developer mode on again in Akai's menu; keys added to `/data/ssh` (the device rounds' Q2 lock) are gone and are added again.

**Not yet seen on the MPC** (the next creator round, [below](#safety-work-before-anyone-else-runs-it)):

- that the hook survives: MPFree starts at the next power-on with the stick in;
- that developer mode stays off: with the stick out, Akai's Developer page shows it off and port 22 doesn't answer. The overlay of `/etc` that developer mode mounts lives in RAM, so whether it comes back depends on what Akai's app does at start, which only the MPC can show. If Akai's app turns it back on at its next start, nothing is harmed (the MPC is as it is today), and the manual's step to switch it off stays the way to do it.

Until the round confirms it, the user manual asks the musician to check that developer mode is off the next time they use Akai's MPC.

## The creator app

### Shape

| Option | Verdict | Why |
|---|---|---|
| **1. One app that builds and writes** | **Recommended** | One download, one window. It can keep the stick's saved settings (partition 4) when rewriting, as `write-test-stick.py` does |
| 2. A builder that makes `stick.img`, written with Raspberry Pi Imager or balenaEtcher | Fallback | Avoids writing our own disk writer, but it is two apps, and those writers erase partition 4 every time |
| 3. The Python tools packaged with a GUI wrapper (PyInstaller) | Prototype only | Fastest reuse, but it drags `debugfs`, `sfdisk` and Python packaging onto macOS and Windows |
| 4. A web page | Not possible | Browsers can't write raw USB disks |

### Technology

A Rust app (ADR-0001), split into a core crate (call it `mpfree-stick`: unpack the update, check its hash, copy and change the root filesystem, lay out the GPT image, verify) with a command-line front end for tests and CI, and a small wizard GUI in `egui`/`eframe` (the owner's choice: pure Rust, one binary per system, no web stack). The project's own `mpfree-ui` draws to a framebuffer, so it isn't used here.

**Editing ext4 on macOS and Windows** is the hardest part, because the builder changes a copy of Akai's ext4 root filesystem with `debugfs -w`. Options:

1. **Bundle e2fsprogs** (`debugfs`, `mke2fs`, `e2fsck`) built for each system and run them as separate programs, keeping the builder's tested command list. They are GPL-2; shipping them as separate programs next to an MIT app is fine with their source offered. Chosen first (owner, 2026-11-15), then not needed:
2. Write the filesystem in Rust. **As built:** not edits to Akai's ext4, but a fresh plain ext2 (no journal, extents or checksums, which Linux's ext4 driver mounts with `ro,noload`) holding every file, link, device, hard link, owner, mode and extended attribute of Akai's, plus the recipe's changes. Partition 4, which must be ext4 and as big as the stick, is made on the MPC with Akai's own `mke2fs` at the first start.
3. Make partition 1 squashfs or erofs, which are simple to write from code. That changes how the hook mounts the stick (`ro,noload` is an ext4 option) and needs Akai's kernel to support it: a hook change, so the owner's call.

The Python builder stays the reference, for development only (16 Nov live run, item 1): the recipe is recorded from its own `build_rootfs`, and a test fails when the two differ. Sticks for the MPC, the device rounds' included, are made with the creator; the builder is for trying a change before the recipe is written again, and for what only it makes (the 3.6.0 kexec jump's build folder, `--akai-app`, `--preload-module`, a stick for an MPC running another release).

**Writing the stick** follows the device rules in the [installer design](usb-installer.md#product-goal) and `write-test-stick.py`: only whole USB disks the system calls removable, within a size range, nothing mounted from them, shown by name and size, a clear confirm, an exclusive open, a read-back compare, and partition 4 kept. Per system:

| System | How |
|---|---|
| Windows | The writer runs as administrator (UAC prompt); locks and dismounts the stick's volumes, writes `\\.\PhysicalDriveN` in whole sectors |
| macOS | `diskutil unmountDisk`, then the raw device `/dev/rdiskN` opened through the system's authorization prompt |
| Linux | `pkexec` (the desktop's password prompt); `umount` of the stick's partitions, then an exclusive open |

Raspberry Pi Imager (Apache-2.0) has solved these on all three systems and is the reference to read.

### Updating a stick

A newer MPFree goes onto a stick that already has it without a new backup (owner, 2026-11-16): writing a stick keeps partition 4, which holds the backup, the setup's done steps, the settings, the library and the Akai kits and samples. The first start then finds every step done and opens the pad player straight away; a step a newer version adds runs alone, from the backup the stick has. A kits file kept from before is counted from its header, so the log's "done: N Akai kits" stays true (the fifth stick said 0).

**A backup made before, shown** (16 Nov live run, item 4). When the wizard uses a backup an earlier start made, it says so for 5 s before it goes on, on a card headed "Using the backup of your MPC already on the stick": when it was made, from the folder's name, how long ago by the MPC's clock (left out when the clock is behind the backup's, as an MPC whose clock was never set would be), and whether on this MPC, from the `MPC:` line ([step 8 above](#the-first-start-wizard-backup-kits-and-samples)): "Made 16 Nov 2026, 01:44 UTC, 19 hours ago, on this MPC". A backup from before the line existed says it does not say on which MPC. The log has the same words after the folder (`first start: using the backup made before: … (Made …)`), never the fingerprint. A backup of **another MPC** (both fingerprints known, and different) is passed over: the newest finished one of this MPC is used if there is one, and otherwise this MPC is backed up too (`first start: … is a backup of another MPC; this one is backed up too`). Nothing is deleted.

**Asking for a new backup.** Under **Keep my backup, settings and files**, **Back up my MPC again too** passes `--new-backup` with `--keep-data`. `write` then puts a random token in `/etc/mpfree-test/new-backup` on partition 1 (`stick::NEW_BACKUP_FILE`, readable by the pad player) and a line in `made-by.txt`. The wizard runs when it finds a token its store has not honoured (`new-backup` in `setup.conf`), even on a stick fully set up or one that gave up: it saves the token before anything runs, starts its tries at 1, marks the backup step not done and keeps `fresh-backup=asked` until a new backup is made, so a failed try asks again at the next start instead of falling back on the old one. The backups already there are kept; the service's room check (7.9 GB free) says when there isn't room.

- **Which sticks.** `disks` marks a USB disk that looks like an MPFree stick (`DiskInfo::mpfree`), without administrator rights: on Linux a partition named `mpfree-test-root` or `mpfree-test-root-off`, on macOS and Windows a volume labelled `MPFREE` (partition 5). It is only a guess for the window's wording; what is kept is decided by `write` itself.
- **The window.** For such a stick, step 3 reads **Update MPFree on this stick**, with two choices: **Keep my backup, settings and files** (the default, with **Back up my MPC again too** and **Bring in Akai's drum kits and samples too** under it, both off by default; button **Update MPFree**, and a confirm without the erase checkbox, which says what is kept) and **Erase everything and start over** (`--fresh-data`; the erase confirm names the backup). The finish page then says **MPFree is updated**: put the stick back and turn the MPC on, with the new-stick steps folded away for an MPC that has lost the start-up helper (whether an Akai update removes it is still open, [below](#still-open)). It tells the two apart by the `write` log's note that partition 4 is kept (`stick::KEPT_NOTE`).
- **Never erasing the backup by surprise.** Keeping passes `--keep-data`: if partition 4 holds an ext2/3/4 filesystem that `existing_data` won't keep (another place or label, from another version), `write` stops before writing anything and says to copy the backup off first (`stick::holds_data`). A partition 4 that never started (still marked) holds nothing, so it is written.
- **The update file.** The stick's system is built from Akai's update file, so step 1 still needs it. Akai's update for the MPC One is a plain `.img` file: the download Akai's page calls the **USB** update, beside the ones for a computer (owner, 2026-11-16). The manual and the window say to choose it; the creator recognises the file by its contents (`AZ01`), whatever its name.

### What ships in the app

- MPFree's own programs for the stick (pad player `mpfree`, startup screen `mpfree-startup`, screen log `mpfree-screen-log`; `stick::PROGRAM_FILES`), built for ARM by the release workflow and carried inside the creator, with the free drum kits (`free-kits`, below); the release's `SHA256SUMS` covers each creator file, and with it the programs. The startup screen was missing from the first creator sticks (2026-11-15: the pad player showed its own star backdrop instead); it is now in the recipe as the builder's `--splash` adds it, and a programs folder without it is refused. With them, when the folder has it, the Plugins place's download helper `mpfree-fetch` (`stick::FETCH_FILE`), linked dynamically against a glibc no newer than the MPC's 2.39 (the device rounds build it with `cargo zigbuild` for 2.34; a release with the runners' cross compiler, as CI does), since the static pad player can't open libcurl itself ([the download helper](mpc-plugin-store.md#the-download-helper-on-the-mpc)). It is optional: without it the stick installs plugins from zips only, and the report says so; one that is static or asks for a glibc newer than the MPC's 2.39 is refused. The process each plugin runs in, `mpfree-plughost` (`stick::PLUGHOST_FILE`), goes beside the pad player the same way, built and checked like the helper, because a plugin needs the MPC's own C library and the static pad player can't load one safely ([plugins](plugins.md#in-the-app)). Without it plugins run in the pad player itself, and the report says that it can't run most of them. Bundling them means one app version is one tested set and works offline.
- A table of supported Akai updates, deny by default. As built it names 3.10.1 by Akai build (`SNAPSHOT-20261107130239`), kernel release (`6.18.44-az01-2026-08-10-rt6`) and the root filesystem's size (453,051,392 bytes), and the record's own SHA-1 is checked; the whole file's SHA-256 is to be added once read from the owner's copy. A hash is not Akai's content.
- **MPFree's own drum kits**, with a provenance list. The pad player can't start without `kits.bin` today, and the kits on the reference stick are Akai's factory sounds, copied out of the owner's eMMC backup by `offline-factory-kit.py`. A musician has no such backup, and Akai's sounds can't ship. The choices (the owner chose **both**, 2026-11-15):
  - **Rendered from MPFree's Drums synth.** CI plays each pad of a few Drums kits once and writes the hits into `kits.bin` (the format in `rust/mpfree-app/src/kit.rs` is plain 44.1 kHz audio, so nothing in the pad player changes). Entirely MPFree's own, nothing to license, but synthetic in character (808/909-style).
  - **CC0 samples.** Public-domain recordings of real drums. More realistic, but each file needs its source and licence recorded, and someone has to choose them.
  - **Both** (chosen): synthetic kits as the default, plus a few CC0 kits.
  - On top of these, **the MPC's own factory kits and samples**, made automatically from the musician's eMMC backup by MPFree's first-start wizard ([above](#the-first-start-wizard-backup-kits-and-samples)). They never ship with the app.

### Developer SSH

The app's **Preferences > Developer options** has one checkbox, **Developer SSH** (off by default). When ticked, the app takes the user's SSH public key file (filled in from `~/.ssh` when there is one), or makes a key pair for them (`~/.ssh/mpfree_ed25519`, never over an existing file), and the stick gets today's key-only root SSH on port 2222 with an ed25519 host key made for that stick; root's locked `!` becomes `*` (key login only) on that stick alone. The app shows the host key's fingerprint and the `ssh` line. Without the checkbox the stick has no SSH server, Ethernet service or keys at all. The user manual's [Installing MPFree](../../user/src/getting-started/installing.md#developer-ssh-for-developers) has the steps.

### Developer routes: kexec-file, LoadPin off, the chain

Merged from the builder (16 Nov live run, item 1). The hook's [opt-in routes](../hardware/soft-reboot-boot.md#the-opt-in-kexec-file-route) are developer options here too, with the builder's flags and rules: `--loadpin-off` only with `--kexec-file`, `--chain` only with both. In the window they are **Preferences > Developer options > How the MPC starts the stick**: Soft-reboot (MPFree's own, the default), Akai's kernel by kexec-file, Akai's kernel with LoadPin off, Chain to the stick's own kernel. Step 3 and the confirm say when one other than the soft-reboot is chosen, and `made-by.txt` gets a `route:` line.

- **What each one writes.** `creator-recipe.py` runs `build_rootfs` once per route and records in `recipe.json`'s `routes` only what differs from the soft-reboot stick: the hook's `jump`, `cmdline` and `kernel.sha256`; for the chain also `/boot/mpfree-kexec/` (the `zImage` link, `kexec.dtb`, `cmdline.txt` and their `SHA256SUMS`, which is a rule the creator hashes), the chain's scripts and units, and Akai's `/usr/sbin/kexec` left unstubbed; Akai's LoadPin unit unmasked on every route but the soft-reboot (`unlinked`); and the hook's list. The command lines come from the builder's `command_lines`, so `root=PARTUUID=` names partition 1's id, which the creator now chooses before it lays the stick out (`Values::root_uuid`). `kernel.sha256` hashes the update's own `/boot/zImage-<release>`. `Recipe::with_route` makes the route's recipe from the soft-reboot one.
- **The chain's device tree.** `kexec.dtb` is built in Rust (`mpfree_stick::dtb::kexec_tree`, a port of `offline-dtb.py` kexec-dtb and the builder's `build_kexec_dtb`): the update's board file plus what U-Boot added on this MPC, read from `--live-dtb` (the pre-flight's `live.dtb`, from `collect-over-ssh.sh --kexec-preflight`), with the eMMC and SD card controllers disabled, `/chosen/inmusic,acvs-emmc-content` dropped and the Ethernet PHY's ID first in its compatible list. The update's board file is also the reference for U-Boot's changes, since the creator only makes sticks for the release the MPC runs; the running tree must be the installed system's (its eMMC controller enabled), for the same board, and a `release.txt` beside it must name the update's release (without one the report says it couldn't check). The report names what changed, never a value: the running tree carries the MPC's serial number and MAC address, which end up in `kexec.dtb` on the stick as with the builder. `creator-recipe.py` also writes `rust/mpfree-stick/tests/data/kexec-dtb-example.json`, a made-up board file and running tree with the builder's `kexec.dtb` and notes for them, and the creator's tests build the same bytes and notes from them.
- **Akai's kexec.** As the builder's `chain_kexec_check`: the chain needs a regular `/usr/sbin/kexec`, and every kexec that `systemd-shutdown` names must be one the chain keeps.
- **Command line** (with the usual options): `mpfree-stick write UPDATE --device DISK --yes-erase DISK --kexec-file --loadpin-off --chain --live-dtb PRE/live.dtb`.

### Releases

GitHub Releases, built by GitHub Actions: one file per system, each with a SHA-256, and a GitHub build attestation once the repository is public. The musician's steps are in [Installing MPFree](../../user/src/getting-started/installing.md).

**As built (2026-11-16):** [`.github/workflows/release-creator.yml`](../../../.github/workflows/release-creator.yml), started by hand (**Actions > USB creator release > Run workflow**, with a box each for Windows and macOS) or by pushing a tag `creator-vX.Y.Z` equal to `rust/mpfree-creator/Cargo.toml`'s version. It never runs on pull requests.

| Job | Runs on | Makes |
|---|---|---|
| `programs` | the self-hosted runners | MPFree's programs for the MPC, built as the device rounds build them (ARMv7, static), checked against `stick::PROGRAM_FILES` read from the source (a program added there without a build line stops the release); and the Plugins place's download helper and the plugin process, `mpfree-fetch` and `mpfree-plughost` (`stick::FETCH_FILE`, `stick::PLUGHOST_FILE`), linked dynamically and checked as CI checks them (ARM hard-float, glibc 2.39 at most); and the free drum kits (`free-kits`, made by `mpfree-free-kits`); with `SHA256SUMS` |
| `linux` | GitHub's Ubuntu 22.04 | `MPFree-USB-Creator-X.Y.Z-linux-x86_64.tar.gz`: one executable with the programs inside (a tar keeps it executable). The job checks the programs are in it byte for byte and that it needs glibc 2.35 at most (Ubuntu 22.04, Debian 12 and newer); built on the self-hosted runners' glibc 2.39 it would need 2.39. It runs the creator's tests and `--cli disks` |
| `windows` | GitHub's Windows | `MPFree-USB-Creator-X.Y.Z-windows-x64.exe`, with the C runtime linked in (`+crt-static`), so no Visual C++ package is needed. Runs the creator's and the disk code's tests, and `--cli disks` through PowerShell's `Get-Disk` |
| `macos` | GitHub's macOS 14 | `MPFree-USB-Creator-X.Y.Z-macos.zip`: `MPFree USB Creator.app` for Apple silicon and Intel (`lipo`), macOS 11 or newer, signed ad hoc (Apple silicon runs nothing unsigned). Runs the tests and `--cli disks` through `diskutil` |
| `release` | the self-hosted runners | `SHA256SUMS` of the three, a build attestation when the repository is public, and the finished **draft** pre-release `creator-vX.Y.Z` with the files and their sums. Running the workflow again replaces a draft's files; a published version is never replaced (raise the version) |

**A developer's build, between releases (2026-11-21):** [`tools/build-usb-creator.sh`](../../../tools/build-usb-creator.sh) builds the `programs` job's files and the `linux` job's creator from the same build lines on a developer's own Linux computer, with the programs inside, in one command, and ends with `rust/target/usb-creator/mpfree-creator` ([Building the USB creator](../guides/build-usb-creator.md)). It links the helpers with cargo-zigbuild against glibc 2.34 when it is installed (the device rounds' way, for a computer whose cross compiler is newer than the MPC's glibc 2.39), and otherwise with the cross compiler, checking either way as the `programs` job does. Its creator uses that computer's Rust and glibc, so it isn't held to 2.35 as a release's is.

The jobs hand files to each other through the draft release itself, never GitHub's artifact storage, which is billed against the whole account and was full from 2026-11-11 ([Artifacts](../guides/testing-and-ci.md#artifacts)). `programs` makes or reuses the draft, clears an earlier run's files from it, and puts up `build-stick-programs.tar` and `free-kits-credits.txt`; each creator job takes the `.tar` down and puts its creator up; `release` takes the creators down for `SHA256SUMS`, puts that up, removes the `.tar`, and writes the draft's text. Release files don't count against that storage, and GitHub's machines can't reach the CI VM. A copy of the programs and of the finished files stays on the CI VM (`/srv/mpfree-store/creator`). [`tools/ci/release_assets.js`](../../../tools/ci/release_assets.js) does the hand-over, from `actions/github-script`.

Why not the formats first planned: an AppImage adds nothing once the programs are inside the executable, needs a downloaded `appimagetool`, and runs from a FUSE mount root can't read (the window passes `$APPIMAGE` to `pkexec` for anyone who packs one). A Windows installer adds an uninstaller and a Start menu entry for a program opened once per update; one `.exe` is simpler.

What it costs and what it needs:

- **Actions minutes.** The repository is private, and GitHub's hosted runners count against the account's monthly minutes (2,000 on the free plan; Windows minutes count twice and macOS minutes ten times). A release is roughly 10 Linux, 10 Windows and 15 macOS minutes: about 180 counted minutes. The minutes ran out on 2026-11-11 and come back with the next billing month. CI itself stays on the self-hosted runners.
- **Who can download it.** A private repository's releases are seen only by its collaborators. Musicians need a public repository, or a separate public one for releases. Build attestations are free only for public repositories, and SignPath Foundation signs only public open-source projects (MPFree is MIT), so all three wait for that choice.

Signing, by system, if nothing is paid for:

| System | Without paying | What the musician sees | Paid option |
|---|---|---|---|
| Linux | Nothing needed | Nothing: the executable comes out of its `.tar.gz` ready to run | None needed |
| Windows | Unsigned at first; apply to **SignPath Foundation**, which signs open-source projects for free | Unsigned: a blue "Windows protected your PC" box on first run; **More info**, then **Run anyway**. Signed: that box fades out as downloads build up reputation | A certificate or Azure Trusted Signing, roughly US$10 a month and up |
| macOS | Unsigned (ad-hoc signed, so it runs on Apple Silicon) | macOS refuses the first open. Since macOS 15 the right-click > Open trick is gone: the user opens **System Settings > Privacy & Security**, clicks **Open Anyway** and enters their password, once | Apple Developer ID, US$99 a year: no warning at all |

The creator is opened once per MPFree update, so a one-time click-through is tolerable if the manual shows it with pictures. Recommendation: launch free (Linux as is, Windows through SignPath once the repository is public and accepted, macOS ad-hoc signed with the Open Anyway steps), and pay for the Apple ID only if beta testers stumble on macOS. As built, the workflow signs nothing beyond macOS's ad-hoc signature; SignPath's signing step would go into the `windows` job, between the build and the upload.

## Akai firmware and legal limits

The owner handles the legal review; this section only records the technical facts that bear on it.

- **Nothing of Akai's is distributed.** The app reads the update file the musician already downloaded from Akai, on their own computer. It links to Akai's download page and never downloads or hosts the file itself, so the musician accepts Akai's terms directly. This matches the [factory content policy](../project/factory-content-policy.md).
- **The finished stick holds a changed copy of Akai's root filesystem.** It is the musician's personal copy, and the app says so: don't share stick images. The project never publishes a prebuilt image.
- **No factory sounds** on a creator-made stick. A later, optional importer of the owner's own content stays local and needs the legal review the policy already asks for.
- **Nothing is circumvented.** The route uses Akai's documented developer mode and script runner and Akai's own running kernel. It doesn't touch the eMMC boot partitions, the verified root filesystem, LoadPin, or any licensing or activation.
- Points for the owner's review: Akai's terms on changing a copy of the firmware for personal use and on studying its format; using Akai's product names (plain "for the Akai MPC One" wording, no logos, a "not affiliated with Akai or inMusic" notice); and the GPL source offer for the bundled e2fsprogs.
